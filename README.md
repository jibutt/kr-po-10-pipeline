# Защищённый конвейер сборки, анализа и тестирования (КР-ПО-10)

## 1. Название проекта
Учебный веб-сервис обращений с защищённым конвейером непрерывной интеграции.

## 2. Назначение
Проект демонстрирует автоматические проверки безопасности, выполняемые при каждом изменении кода: тесты, статический анализ (Bandit), анализ зависимостей (pip-audit), поиск секретов (gitleaks) и шлюз, блокирующий слияние при нарушениях. Все учётные данные в проекте синтетические.

## 3. Требования к среде
- Python 3.12
- Git 2.40 или новее
- Для локального запуска анализа: gitleaks 8.18.4 (контрольная сумма архива указана в security.yml)
- Для CI: GitHub Actions, образ ubuntu-24.04

## 4. Порядок установки
```
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
```

## 5. Порядок запуска
Сервис создаётся фабрикой `app.create_app(db_path)`. Пример запуска:
```
python -c "from app import create_app; create_app('tickets.db').run()"
```
Учётные записи задаются в конфигурации приложения (`USERS`) в виде хешей паролей. В тестах используются синтетические учётные записи из `tests/conftest.py`.

## 6. Порядок запуска тестов и анализа
```
python -m pytest -q
bandit -r app -ll          # статический анализ, Medium и выше блокирует сборку
pip-audit -r requirements.txt
./gitleaks detect --source . --redact
```
Ожидаемый результат на основной ветке: все команды завершаются с кодом 0.

## 7. Сведения об исходных данных
Исходные данные синтетические: пользователи `alice` и `bob` и их пароли существуют только в тестах. Тестовые обращения создаются в базе SQLite во временном каталоге.

## 8. Известные ограничения
- Bandit находит типовые шаблоны и не выявляет ошибки логики.
- pip-audit проверяет только зафиксированные версии из requirements.txt и зависит от полноты баз уязвимостей.
- Анализ ограничен языком Python.
- Порог Bandit выбран после пилотного запуска (см. раздел 2.3 пояснительной записки): первоначально рассматривался уровень High, но он не обнаруживает SQL-инъекцию с уровнем Medium.
- Тесты безопасности покрывают перечисленные сценарии и не доказывают отсутствие уязвимостей.

## Контрольные дефекты
Контрольные дефекты вносятся только в отдельные ветки и не попадают в main.

- `control-sql`: небезопасное формирование SQL-запроса в `app/storage.py` (ожидается блокировка Bandit).
- `control-secret`: файл `docs/control/test_key.txt` с тестовым ключом AWS из документации (ожидается блокировка gitleaks).
- `control-dep`: добавление `requests==2.19.1` в requirements.txt (ожидается блокировка pip-audit).
